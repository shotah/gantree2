Install — local, Cloudflare, or home

Same Worker, same wrangler.jsonc, three places it runs. The harness is the Agent Durable Object and opens no listen port. The same Worker is the Vinext app and serves the HTTP API, including the mailbox at /ws/<slug>.

Place Command State Reach it at
Local dev npm run dev in-memory, .wrangler/ http://127.0.0.1:3000
Cloudflare wrangler deploy (CI) Workers · DO · KV https://gantree2.bldhosting.com (custom domain in wrangler.jsonc; a fork edits routes or drops it for workers.dev)
Home (Mini / NUC / VM) npm run deploy:home (celld deploy) celld Tailscale HTTPS or a Cloudflare Tunnel

Need Node 22 (node -v). Distro apt install npm is often Node 20 and will fail.

Google OAuth client

gantree does not create this. GCP → APIs & Services → Credentials → Create credentials → OAuth client ID.

Field Value

Place Redirect URI
Local dev http://127.0.0.1:3000/api/auth/callback/google (Google accepts loopback http)

Google rejects private LAN IPs (http://192.168.x.x). A home box must sit behind Tailscale HTTPS or a Tunnel for sign-in to work. One client can carry all three redirects.

Consent screen: External (or Internal if Workspace-only). External + Testing → add yourself as a test user.

Local dev

git clone https://github.com/shotah/gantree2.git
cd gantree2
cp .dev.vars.example .dev.vars
# .dev.vars: GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, SESSION_SECRET (≥32 chars),
#            GANTREE_ADMINS=you@example.com
npm ci
npm run dev            # http://127.0.0.1:3000 → /login

Sign in. You are admin. A second Google account gets not_allowed until you add it on /users.

Without a Google client: GANTREE_DEV_USER=118212345678901234567:you@example.com in .dev.vars fakes a session on loopback only. The sub is 10–32 digits. It still has to be in GANTREE_ADMINS or GANTREE_ALLOW. Details: access.md.

npm run dev is Vite on 127.0.0.1:3000. It serves the Durable Objects and the harness. Screenshots in this repo were taken against npm run dev. npm run build && npm run start is the built Worker under Miniflare (dist/server/wrangler.json); use it when you want the production bundle, not to get Durable Objects.

Chat with a real agent locally

With house LLM_BASE_URL, LLM_API_KEY, and LLM_MODEL in .dev.vars, run npm run agent. It starts Vite (Worker, Durable Objects, native harness) unless something healthy is already on port 3000, ensures a local agent (default slug kit), and restarts the Agent Durable Object so nativeBrain opens with those house keys and, when agent config leaves them blank, fills CHAT_MAILBOX_URL (ws(s)://<origin>/ws/<slug>) and CHAT_BEARER (the room bearer) so chat__avatar_update can set the face. PUBLIC_ORIGIN is that origin when it is set. When IMAGE_OUTPUT_DIR is blank, the same harness uses /images. Those bytes live in the Agent DO sqlite table image_output, which is the handoff photo_generate gives to chat__avatar_update and chat__backdrop_update. Chat at http://127.0.0.1:3000/chat/kit (or --slug ada). Set GANTREE_DEV_USER and list that identity in GANTREE_ADMINS so loopback API calls can create the agent without a browser session. The script also puts that user on the agent room, which is what opens the chat socket. The harness is the Agent Durable Object that deploy ships.

House keys the harness reads from .dev.vars (and, in production, from Worker secrets): LLM_BASE_URL, LLM_API_KEY, LLM_MODEL, and optionally SEARCH_API_KEY and SEARCH_PROVIDER. An agent's own config.env wins when the same name is set on both. Other keys live on the agent. Feeds publish with no key; FEEDS_USER_AGENT only overrides the User-Agent, which defaults to gantree/<version> (+https://gantree2.bldhosting.com). The Keys fold suggests every row below (search keys are listed once under websearch; the Worker may still set them as house secrets). How each provider registers the catch is in auth.md. CRON_TZ, DAILY_PLANNER_AT, MEMORY_CONSOLIDATE_MINUTES, DYNAMIC_TOOLS, MCP_ENABLE_FORCE, and PUBLIC_ORIGIN are harness knobs. PUBLIC_ORIGIN is the catch host, with no path.

Open http://127.0.0.1:3000/chat/<agent id> after you create the agent. Blank keys on a new agent use the house LLM_* from .dev.vars. The browser only ever sees the key names (GET /api/tools → house). In production, set them with wrangler secret put and new agents need no keys of their own.

npm run seed -- --vars   # writes .dev.vars.shot from .dev.vars (placeholder identity)
npm run dev:shot         # the same dev server, reading .dev.vars.shot
npm run seed             # fills Kit and Ada through the HTTP API
npm run shot             # headless Chrome → assets/docs/*.png. CHROME_BIN overrides the Chrome path.

Pictures never carry a real account. npm run seed derives .dev.vars.shot (git-ignored) from your .dev.vars: every secret is copied, but GANTREE_DEV_USER and GANTREE_ADMINS become the placeholder 100000000000000000001:dev@example.com and GANTREE_ALLOW is emptied. npm run dev:shot is CLOUDFLARE_ENV=shot, which makes the Cloudflare Vite plugin read that file instead of .dev.vars; your real .dev.vars stays as it is for the Google walk. Seed refuses to run against a server signed in as anyone but the placeholder, and tells you to restart with dev:shot whenever it mints bearers. Shots wear the Neon theme by default; GANTREE_SHOT_THEME=<id> picks another. npm run shot opens /chat as the dev user. A member picker needs GANTREE_SHOT_AS_MEMBER=1 against a server whose .dev.vars.shot has no GANTREE_DEV_USER (seed writes the member cookie).

GITHUB_TOKEN is automatic (ci, pages, release). The deploy-cloudflare job fails fast if any of the four auth values (GOOGLE_CLIENT_ID, GOOGLE_CLIENT_SECRET, SESSION_SECRET, GANTREE_ADMINS) is empty.

Not in GitHub. The house keys that let a new agent run with no keys of its own (LLM_BASE_URL, LLM_API_KEY, LLM_MODEL, SEARCH_API_KEY, SEARCH_PROVIDER) are Worker secrets, set once from a laptop with the same Cloudflare token:

npx wrangler secret put LLM_BASE_URL     # and LLM_API_KEY, LLM_MODEL, SEARCH_API_KEY

Never set in production: GANTREE_DEV_USER (loopback dev door) and CHAT_SECRET (loopback two-tab spike). AGENT_BEARERS is an override; the Agent DO mints bearers itself.

Outside GitHub and Cloudflare, the remaining owner steps are the Google client redirect URIs (above) and the tools' provider consoles (auth.md).

Cloudflare

CI does it, with the GitHub settings above. Push to main. ci.yml runs tests, lint, typecheck, build. deploy-cloudflare.yml then creates the gantree2-directory KV namespace if it is missing (the TODO id in wrangler.jsonc is patched for that run only), runs wrangler deploy --var … and wrangler secret bulk. It fails fast if any of the four auth values is empty. Add the Worker origin to the Google client's redirect list, and the catch URIs in auth.md to the tools client.

By hand from a laptop (same token in your shell), once:

npx wrangler kv namespace create gantree2-directory   # paste the id over "TODO" in wrangler.jsonc
npm run deploy
npx wrangler secret bulk < secrets.json   # {"GOOGLE_CLIENT_SECRET":"…","SESSION_SECRET":"…"}

The Worker, Durable Objects, and KV are the pieces monetize.md prices.

Home (celld)

celld runs the Workers platform on your own box from the same wrangler.jsonc: Workers, Durable Objects, KV, and static assets. Install per its README.

# on the Mini
cat > /etc/gantree/vars.env <<'EOF'
GOOGLE_CLIENT_ID=…
GOOGLE_CLIENT_SECRET=…
SESSION_SECRET=…
GANTREE_ADMINS=you@example.com
GANTREE_ALLOW=
EOF
chmod 600 /etc/gantree/vars.env

git clone https://github.com/shotah/gantree2.git /opt/gantree
cd /opt/gantree && npm ci
CELLD_VARS_FILE=/etc/gantree/vars.env npm run deploy:home

Put a hostname in front:

Tailscale (preferred): tailscale serve --bg https / http://127.0.0.1:<celld-port>. Redirect URI is https://<mini>.<tailnet>.ts.net/api/auth/callback/google.

Cloudflare Tunnel (zone already on Cloudflare, no WAN ports): cloudflared tunnel run with the public hostname → http://127.0.0.1:<celld-port>.

Do not open a router or cloud firewall port to the world. celld stops on any wrangler.jsonc key it does not model, so a manifest that deploys to Cloudflare deploys here, or tells you exactly why not.

Home deploy is not a GitHub Action. GitHub cannot reach the Mini and should not.
